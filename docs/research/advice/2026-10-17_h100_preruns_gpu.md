## Accounting and acceptance contract

**Freeze K2:** `--learner-fast --batch-scale 2 --lr-scale none --update-every 1
--learner-precision fp32`. This is 256 newly ingested transitions per optimizer update,
with 768 replay rows and 256 anchor rows, not a 256-row SGD minibatch:
`research/redesign_m3c_20261008/learner_m3c.py:88-89,655-662` and
`research/redesign_m3c_20261008/train_m3c.py:178`. Keep reward, labels, schedules,
target sync, weight publication, replay capacity, initialization and sampling fixed.
Do not use K4 or `--update-every 2` to cross a fixed-recipe speed bar.

Let U be completed optimizer updates/s; R be valid consumed learner transitions/s;
M be the matched Mac rate; C be the matched Colab A100 rate; p be the observed H100/A100
units-per-hour ratio. Frozen-seat actions and padded inference rows do not count in R.
Maintain D (actual learner decisions) separately from emitted valid n-step rows R: the
current trainer increments these differently (`train_m3c.py:3371-3379,3405-3413`). Final
reconciliation must itemize emitted rows, startup accounting, 256-row update tokens,
completed/pending updates, remaining update debt and actor n-step tails. Do not require
the historical decision odometer divided by updates to equal exactly 256. The old Mac/
A100 rates below are decision-rate proxies; extract matched emitted-row rates before
using them as a binding R comparison.

- **Operational GO:** clean exits, hash-complete receipts, no ring overrun, finite
  losses/gradients, no skipped optimizer steps, and reconciled transition/update counters.
  Permit at most 2% window-boundary discrepancy from R/U=256, with exact final accounting.
  Missing evidence or an interrupted window is INVALID/INCOMPLETE, not KILL for the algorithm.
- **Engineering 4×:** require R >= max(21,600, 4M) and U >= R_target/256 in every final
  repeat, plus setup/transfer/cleanup-inclusive projected step speedup >=4×. With the
  recorded self-play Mac M=5,459 this is R>=21,836 and U>=85.297; 84.375 is only the
  rounded 21,600 target. For league roles, use their own matched M.
- **Credit efficiency:** H100 pays per unit only if its matched useful-work rate ratio
  exceeds p. At the owner's planning p=1.5 and descriptive A100 U=62.2, break-even is
  U>93.3, not 84.375. Prefer >=1.10p for a deployment margin; measure C again if code,
  roster or CPU allocation differs. Being 4× Mac and being cheaper per unit are separate.
- **Lag/stability:** compare mean and p95 weight-version lag to the frozen same-roster,
  same-queue control; neither may increase. Record seconds of age too. No missing p95,
  monotonic queue growth, swap, or memory growth >5% between the first and last scored
  thirds. Reject a >10% decline between those thirds as nonstationary. Keep queue frames
  at 4 initially; reducing to 2 is an explicit measured arm, not a hidden freshness fix.
- **Repeat rule:** short screens use two independent warmed windows per cell, alternating
  control/treatment order. An optimization advances at >=10% median U gain and >=5% in
  each pair, with the above guards. A valid 5–10% median gain gets one bounded EXTEND;
  <5%, a regression, or a guard failure KILLs that optimization. An extension must meet
  the original GO rule; no further tuning/retry. Finalists need three independent
  10-minute post-warm-up runs. Performance GO never means scientific GO.

Register source/config/input/checkpoint hashes, exact row order, seeds, warm-up condition,
measurement windows, failure precedence, permitted extension and caps before each packet.
Use at least 120 seconds of warm-up for final integrated runs, after compilation and
replay readiness; verify graph replay rather than assuming elapsed warm-up suffices.
Profiles run in separate unscored windows. Warm-up, compile, uploads and shutdown remain
in billed and projected end-to-end time. Do not score an opportunistically selected tail.

Python-3.12 isolation helper is at `research/t16_colab/environment.py:11-35`.

Refresh the matched Mac baseline only on available capacity, retaining concurrent-load
metadata. Use the same B8 initialization and input bundle as the H100 cells, 128 worlds,
two actors, Apple `--device mps --actor-device mps`, eager learner/actors, and identical
K2 recipe. Raw/g3 versus packed/g0 is a measured storage choice; the old packed baseline
cannot qualify a future mixed-slot implementation. If existing jobs prevent a defensible

**GO** to hardware measurement only after parity, accounting and cleanup tests pass.
**KILL** adoption of any implementation that changes gathered bytes or loses messages.

### 1. Establish the H100 learner ceiling without actors

Run matched fp32 K2 eager and `reduce-overhead` cells, raw rings/g3, then g0 as the host
control. Use B8 weights and identical synthetic ring contents. Record medians and each
round, gather ms, serialized device-leg ms, wall ms/update, compile time, graph/canonical
fractions, clocks/power/memory and actual H100 SKU. A fixed-batch synthetic result is an
upper-bound diagnostic; it excludes actor features, real ingestion and label scarcity.

**GO to contention tests** if fp32 U>=106 in every warmed round: this leaves approximately
20% headroom for the observed 62.2/78 retention ratio and the rounded target. It is a
planning margin, not an H100 prediction. **EXTEND to packet 2 only** at 84.375<=U<106,
because the integrated result decides whether the margin is adequate. **KILL the current
fp32 H100 configuration for the 4× objective** if U<84.375; retain bf16 diagnostics only
if a separate precision arm is still of interest. This does not prove H100 can never
improve or justify changing batch size.

Try `max-autotune-no-cudagraphs` only if the eager/graph contrast and trace leave a
specific kernel-selection question, in the same bounded registration. It is an existing
flag, unlike a new custom CUDA kernel. Require the general >=10% integrated gain before
adoption. Do not start a broad compiler-mode sweep or a Hopper-specific kernel port.
Hopper adds hardware resources and execution features, but neither the peak BF16 FLOP
rate nor TMA implies a speedup for this fixed network without kernels that use them
([NVIDIA Hopper tuning guide](https://docs.nvidia.com/cuda/hopper-tuning-guide/index.html)).

### 2. Recover actor-forward contention without changing the learning recipe

Fix fp32 K2, raw/g3, 128 worlds, four CUDA actors, queue=4 and compiled learner. Measure
the 2×2: actor compile `{off, reduce-overhead}` × NVIDIA CUDA MPS `{off,on}`. Two 120-second
scored windows per cell plus bounded warm-up fit a screening packet only with cached
compilation; otherwise defer an unstarted cell explicitly. Confirm the winner in 4b.
The actor path already pads all-slot batches and updates weights in place
(`research/redesign_m3c_20261008/train_m3c.py:2641,2752-2758`;
`research/redesign_m3c_20261008/compile_m3c.py:239-330`). Eager refresh currently moves
the model CPU→GPU, so a gain may include removal of refresh copies, not just fewer launches.

Collect a separate short device trace with learner and actor process IDs, H2D/D2H,
weight refresh, CUDA launches, graph replay and synchronization. Measure learner-only
time again after each contention condition; do not subtract overlapping host and GPU
timers. If removal of actor work restores the ceiling while gather is unchanged, that
supports interference; the trace must distinguish compute contention from launch gaps.

**GO** enables the winning graph/MPS combination only under the general gain, lag and
stability rule and confirmed Colab support. **KILL** an optimization below 5% or on
fallback/identity/lifecycle failure; retain the simpler configuration. **EXTEND** the
5–10% band once. If ordinary actors already meet the final speed/economics gates, MPS
need not be deployed for a marginal gain.

Actor qualification must include saved real observations, exact/near Q ties, legal masks,
changing live-row counts and repeated weight refresh. Require byte-identical features and
zero masked-action/v8-label differences from eager on that corpus. The existing random-Q
probe records argmax flips but does not reject them specifically
(`compile_m3c.py:264-300`); passing it alone is insufficient. A nonzero difference requires
a separately registered numerics arm, not the claim of a transparent performance fix.
Learner compile already permits bounded floating-point reassociation; retain its existing
gradient checks and disclose that boundary.

CUDA MPS is an external process-sharing service; it is unrelated to Apple's MPS device.
Use a fresh dedicated runtime, job-owned pipe/log directories and an owned daemon started
before any CUDA client. Verify every client connects and shut down owned clients before
the daemon. Start with no active-thread quota. A quota is a limit, not reserved SMs;
do not apply an arbitrary 80/20 split. NVIDIA describes MPS benefits for underfilled
kernels, not a guarantee for an already saturated learner
([MPS guidance](https://docs.nvidia.com/deploy/mps/when-to-use-mps.html)). Do not change
compute mode or an existing daemon. If Colab does not permit it, select the measured
MPS-off fallback. Graphs reduce launch overhead but do not merge processes; actual graph
eligibility must be checked ([PyTorch 2.9 compile](https://docs.pytorch.org/docs/2.9/generated/torch.compile.html)).

### 3. Explain the bf16 reversal before considering adoption

The diagnostic arm changes **learner** precision only. Actors stay fp32. Autocast forwards
with Q cast back up for loss are implemented at
`research/redesign_m3c_20261008/learner_m3c.py:21-26,442-449`; cast-up does not restore
precision already lost in Q/targets. This is a registered numerics arm at unchanged 256
cadence, not a faster spelling of fp32.

Compare fp32/bf16 with actors absent, then with the same recorded fp32 actor-forward load,
then with real actors. Use the winning scheduling configuration from packet 2, holding
every other knob fixed. A minimal saved-observation load driver is needed to replay the
same shapes and refresh cadence without letting a different learned policy change body
lengths or CPU cost. It is a diagnostic only and cannot produce a scientific checkpoint.
Start with the ordinary four-actor fp32/bf16 pair; run the replay control if the reversal
persists. Limit replay load tests to the one observed discrepancy, not an extra full matrix.

| Hypothesis | Discriminating evidence and action |
|---|---|
| Compile failure, recapture or partial anchor batches | Compare fallback reason, actual compiled calls, canonical n/m, graph counts and warm-up. `_canonical` permits full agent rows and zero/full anchor rows (`learner_m3c.py:728-738`); partial batches may be eager. Fix the identified defect; never relax verification tolerance to obtain speed. |
| GPU competition or refresh traffic | Fixed input/forward replay reproduces the slowdown; device trace shows longer learner kernels or launch/sync gaps. Keep fp32 unless packet 2's scheduling fix removes it in real runs too. |
| Host starvation or changed trajectories | Replay control is fast but real actors slow; queue-only wait, gather and length-binned feature cost rise. Keep precision and actor supply diagnoses separate. bf16 may change rollout distributions. |
| Precision implementation overhead | Device trace shows cast/layout/unsupported-kernel overhead even without actors. Retain fp32; tensor-core peak is not relevant evidence. |
| Different clocks, CPU quota or transient startup | Metadata/window mismatch or order-dependent results. Mark invalid/nonstationary and use the one registered extension after resolving the cause. |

**GO only to a separate learning-quality screen** if bf16 is >=20% faster end-to-end than
the matched fp32 winner in all final repeats, all general guards pass, and the discrepancy
has an attributable explanation. Require finite one-step loss/gradients/parameters on
saved real batches and the existing compile-versus-eager same-precision verification;
report bf16-versus-fp32 Q/action/TD/gradient differences without calling them equivalence.
**KILL bf16 for this long run** on numerical failure, unresolved slowdown or <10% gain.
**EXTEND once** at 10–20%; adoption still requires >=20% and independent quality evidence.

A one-hour speed test cannot qualify RL quality. Default the first long run to fp32 if
the five-replica, fixed-transition quality comparison has not passed its own registered
development GO and survival guards. Final promotion still needs fresh strict Tier 1 and
Tier 2. Do not add fp16, FP8 or a new TF32 setting to this packet. Record effective
matmul/cuDNN TF32 and reduction settings: “fp32 tensors” is not proof that every multiply
used IEEE fp32, and defaults must not be assumed across versions
([PyTorch CUDA semantics](https://docs.pytorch.org/docs/2.9/notes/cuda.html)).

### 4. Test the CPU budget and the workload the long run will actually use

**4a, screen:** use the fp32 winner and measure 2/3/4 actors at fixed g3, then the best
actor count at g0/g2; this avoids smoke-03's confounded a2/g0→a3/g3 comparison. One thread
each for Torch, BLAS/OpenMP and Numba initially. Gather workers are additional threads,
not covered by `NUMBA_NUM_THREADS=1`. Add six actors only if four remain demonstrably
actor-limited and the effective CPU budget supports them. Do not count SMT siblings as
independent full cores or equate pod vCPUs with Colab performance.

Record `lscpu -e=CPU,CORE,SOCKET,ONLINE`, `os.sched_getaffinity(0)`, cgroup CPU quota,
throttling deltas, per-process CPU time, run queue, RAM/swap, queue-only wait and
feature/forward service time. On RunPod, optionally constrain the owned benchmark group
to six physical cores with their SMT siblings, and a smaller three-core/six-thread
allocation. This is a CPU-count sensitivity test, not a Colab emulation: clock, cache,
NUMA and cgroup throttling still differ. Only the Colab check resolves that transfer.

**Choice rule:** choose the smallest actor count within 5% of the fastest valid U, provided
it meets the final speed target and lag guards; choose the smallest gather pool within
3% of its valid best. If CPU throttling consumes >5% of elapsed time or the run queue grows
while U falls, KILL that oversubscribed setting. Use raw rings on local scratch when peak
RSS remains below 80% of the effective RAM limit and there is no swap. Otherwise test
lossless packing explicitly; `/dev/shm` capacity must cover the measured rings with 20%
headroom. Neither Drive FUSE nor an undersized `/dev/shm` belongs in the hot path.

**Actual league prerequisite:** after mixed-slot dispatch exists, repeat the selected
configuration for N=3 main and N=1 exploiter workloads with the real protected pool,
including dynamic BV8 identities/cache misses and vector61/v8 opponents. Profile live
learner/frozen row counts and report only learner decisions in R. N=6 is the control,
not a replacement for N=3. Include separately labeled short/long-body corpora (at least
lengths 150/600/1200) and one fresh advancing run; synthetic restored states are not
training-quality evidence. The existing actor plan already supplies the measurement
design and warns that long-body v8 cost grows sharply
(`docs/research/specs/actor_throughput_plan_2026-10-17.md:118-139,366-408`).

**4b, confirm:** three independent 120-second-warm-up + 600-second-score runs per
finalist, one finalist per <=60-minute packet. Each actual role needs its own complete
confirmation; do not pool N=1 and N=3 rates. **GO** only on all-repeat accounting, speed,
lag and stability passes. **KILL** the H100 route for a failing role, not the league
hypothesis; run that role on Mac or redesign placement in a new registration. If a full
league implementation is unavailable, finish hardware diagnostics and HOLD the long
league run. `--all-snakes-learner` and `--mixed-frac` do not implement mixed learner seats
(`train_m3c.py:1643-1649`; `lane_a_league_design_2026-10-17.md:18,85-95`).
