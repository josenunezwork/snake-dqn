## 2. What perf-sim changes (byte-identical)

All changes are in non-pinned files (`src/game/*`, `src/scripts/tournament_eval.py`). The
seven veto sources pinned by the v8 strict receipt and the serving registry
(`src/evaluation/safety_veto*.py`) are untouched, so the served wrapper's
`wrapper_sources_match` and every strict spec's source pins still hold.

1. **Exact integer radius tests.** `distance(a, b) < ss` on integer coordinates is
   `dx*dx + dy*dy < ss*ss` whenever the libm's `pow(x, .5)`/`sqrt` are exact at `ss**2` and
   within 1 ulp elsewhere; `game_logic.exact_radius_sq` checks this per radius at runtime
   and returns `None` (original float path) otherwise.
2. **Per-snake geometry cache** (`src/game/snake_geometry.py`): cell buckets of a snake's
   collision points, its body cell set and its neck-to-tail cell set, keyed by game id and
   validated on content (segments tuple, length, cell size), so a hit is a rebuild. Shared
   by the five observers of each snake in a phase and between the end-of-frame (live) and
   next-frame (snapshot) phases.
3. **Bucketed neighbourhood queries** for the mask simulation (3x3 cells) and per-action
   danger (7x7 cells: only distances below `3*ss` can change any output).
4. **Free-space flood fill:** inlined rectangular bounds; a start already seen by an earlier
   flood of the same call reuses that flood's count (`min(cap, |component|)` is
   order-independent); a per-snake result cache keyed by content (the hero's veto
   recomputes what its carried state computed one call earlier).
5. **Danger map:** exact far-point skip (`d2 > (300 px)**2`), `update_danger` and
   `_angle_to_sector` inlined with the same expressions.
6. Inlined `same_cell` in food pickup / overlap and in the self/body collision checks;
   scripted-anchor food cells memoized on content.

Not done, on purpose: batched torch forwards (batch-N Q differs from batch-1 Q by up to
~6e-6 here; `torch.equal` is False even at batch 2), any change inside the pinned veto
modules, numpy/vectorized `atan2` (NumPy's `arctan2` is not guaranteed to round like libm's
`atan2`; a 1-ulp change can move a sector boundary).

## 3. Measured speedup (Mac) and identity evidence

Paired A/B (`ab_bench.py`: both trees play the same episodes concurrently, one shared slot
each, 1 torch thread; `results/ab_bench.json`):

| Workload | main db2ef7a | perf-sim | Speedup |
|---|---:|---:|---:|
| Strict-world H5000 eval episode, frp3-s12 + v8, 3 mixes (worlds 20-21, both arm orders, 12 eps/arm) | 111 eps/h/core | 233 eps/h/core | **2.10x** (per-episode 1.72-2.34x) |
| Same, worlds 0-1 (6 eps/arm, earlier perf-sim commit) | 92 eps/h/core | 224 eps/h/core | 2.42x |
| FRP-v3 gate-world training actor (H3000, eps 0.1, v8-routed exploration; frp-v3 tree +/- the perf-sim `src` diff) | 145 rows/s | 317 rows/s | **2.19x** |
| Default Apex actor arena (0.2-scale board, short snakes) | 2031 rows/s | 2634 rows/s | 1.30x |

The gain grows with snake length (the replaced scans were O(total segments) per query): long
H5000 bodies in the strict world gain most; the tiny training arena gains least.

After perf-sim (`results/profile_final_eval.txt`, same 6 episodes: cProfile total 485 s ->
192 s) the largest block is the **v8 veto chain (23%)**, which is pinned code (v3/v5/v7 Python
floods), then the safe-action simulation (18%, mostly geometry builds), danger map (10%),
food/enemy features (10%), free space (8%), per-action danger (7%), torch forward (5%).

**Identity** (`results/identity_summary.json`, `compare_identity.py`, all identical):

* 42 strict-world H5000 eval episodes (14 worlds x frozen/scripted/mixed; 210k frames; the first 30
  alone had 10 hero deaths of 4 causes and 167 veto replacements incl. 20 head vetoes): per-frame world digests
  (all snakes' segments/direction/length/alive/boost/chosen action, food, Python + NumPy RNG
  state), every network forward's input and output float32 bytes (730k rows), the canonical
  record and the timing-stripped v8 diagnostics.
* 15 FRP-v3 gate-world actor episodes (H3000 and H5000, hero deaths included; 55.9k buffer
  rows: states, next states, actions, rewards, dones, bootstrap steps, masks, priorities).
* 23 default-arena actor episodes (9.9k buffer rows).
* 0 non-int coordinates seen (the integer fast paths' precondition), every frame.
* Unit oracle tests against verbatim copies of the replaced functions on adversarial random
  worlds (`tests/test_perf_sim_identity.py`, 18 tests, mutation-checked).

**Pod effect (estimate).** The work is pure-Python integer/set code, so the ratio should
carry to x86 roughly unchanged (the exact-radius checks also hold for glibc; the code
re-checks at runtime and falls back if not). From
`docs/research/runpod_x86_consistency_2026-10-03.md`: a cpu3c vCPU is ~3.6x slower than an
M5 P-core and a live H5000 episode took ~91 s with 2 threads (2 vCPU) there. With perf-sim
(2.1-2.4x) and one single-thread episode per vCPU, expect ~40 s per episode on an otherwise
idle core and ~60-70 s with both SMT siblings busy, i.e. ~1.25x more episodes per core than
one-per-core and roughly 2.6-3x the old episodes per dollar (old ~660 episodes/$ on cpu3c
-> ~1,700-2,000). `pod_bench.py` measures this before anyone relies on it.

## 4. One episode per vCPU (SMT) on pods

**Why.** A RunPod vCPU is a hyperthread (`runpod/NOTES.md`): an SMT sibling adds ~25%
throughput to a physical core. Billing is per vCPU, so running one episode per *physical*
core (or 2 torch threads per episode, as the fan-out runner does now with
`FANOUT_THREADS=2`) leaves the paid sibling idle. Episodes are effectively single-threaded
(the MLP forward is ~3% of the time; intra-op threads add nothing at batch 1).

**Prediction.** Per-episode wall time rises ~1.6x when both siblings are busy, aggregate
throughput rises ~1.25x versus one episode per core, and ~2x versus the current
"2 threads per episode" layout on the same pod (half as many episodes in flight, each barely
faster).

**Benchmark (prepared, not launched).** `research/perf_sim_20261007/pod_bench.py` runs the
sweep 1 / physical cores / all vCPUs / 1.5x vCPUs single-thread processes on the same
worlds, reports episodes/hour and episodes/$ per step, records lscpu / model / SMT layout /
the exact-radius checks, and compares every mass integral with a Mac reference file.
Suggested run: one cpu3c-16 (or the smallest size with stock; 8 is enough to see the SMT
effect) for ~15 min, ~$0.12-0.25; then the same on cpu5c when it has stock. Needs: git
archive of the perf-sim commit, the venv, the five checkpoints as `<sha256>.pth`
(`SNAKE_PERF_CKPT_DIR`). Owner approval required before any pod (RunPod rules).

**Then** set the fan-out runner's default to one episode per vCPU (`FANOUT_THREADS=1`,
slots = vCPUs) if the sweep confirms >= 1.15x aggregate over one-per-core.

## 5. cpu5c vs cpu3c (speed per dollar)

cpu5c costs 17% more per vCPU-hour ($0.035 vs $0.030). It wins on episodes/$ only if a
cpu5c vCPU is >= 1.17x faster than a cpu3c vCPU on this workload. cpu3c is a mix of Zen 2/3/4
(EPYC 7352/7713/9334 seen), cpu5c is marketed at up to 3.75 GHz with DDR5 (likely Zen 4/5).
Single-thread pure-Python speed tracks clock and IPC: Zen 4 at ~3.7 GHz vs Zen 3 at ~3.0-3.5
GHz is plausibly 1.2-1.4x, vs Zen 2 more. So cpu5c is probably *slightly* better per dollar
and clearly better per wall-hour, but stock is thin (EU-RO-1 / EUR-IS-1, <= 4 vCPU on
2026-10-06). Decision rule: run `pod_bench.py` on one of each (same sweep); prefer cpu5c when
its measured episodes/$ is >= cpu3c's, else cpu3c; record the CPU model in every intent
(the flavor does not pin a model, so re-check per pod).

## 6. The larger vectorized-sim project (blueprint P2, vector61 path)

**State.** `src/simd_env/` already has a bit-exact NumPy BatchSim (raster/PQN stack) and a
vector61 path for Apex checkpoints (`vector61_featurizer.py`, `vector61_policy.py`,
`eval_engine.run_simd_eval(vector61=True)`): ~3.65x vs live with the v2 veto, ~2x with v5,
less with v7/v8 because the hook runs the live Python veto on row views (branch
`simd-v7v8`, unit parity only, H5000 parity check prepared but not run). It is eval-only:
no actor/training loop runs on it, and batched forwards are not bit-exact (rowwise forward
is the identity-safe default).

**What "very fast" needs, in order of payoff:**

1. **Land perf-sim** (this branch; the live engine is the identity reference for
   everything, so making it 2.4x faster speeds every gate, screen, serving qual and the
   training actors at once, with no governance change). ~0 days left beyond review.
2. **v8 on SIMD at H5000** (finish `simd-v7v8`: run its prepared H5000 parity check, then a
   Tier-1 A/A). The v8 hook's floods are the live code and now dominate a SIMD frame; port
   them as array floods only if the A/A shows SIMD+v8 < 2x live+perf-sim. 2-4 days.
3. **Actor on SIMD** (gate-world training actors stepping E envs per process with the
   vector61 featurizer, hero-only transitions, v8-routed exploration). This is the real
   training multiplier: one process could produce ~E x the transitions of a live actor at
   ~0.3-1 ms per env-frame. Needs: the gate roster sampler and v8 explore filter on rows,
   n-step/terminal semantics identical to `ApexActor._run_gate_world_episode`, and a
   transition-level identity harness (this branch's `actor_harness.py` digests are the
   template). 6-10 days including parity, plus a fidelity re-run (FRP-style F1-F6).
4. **Numba / compiled flood kernels** for the remaining Python floods (v3 tail-aware
   reachable, v7 landing areas) — only after a governance decision, because the veto bytes
   are pinned by receipts: a compiled twin must be shown identical and re-pinned.
   2-3 days + review; needs `numba` added to requirements (not installed today).

**Estimate.** 2+3 = ~2-3 weeks solo for a training actor that is ~5-10x a perf-sim live
actor per core (projection from the SIMD per-env-frame costs above; not measured end to
end), and eval at ~3-4x live on all vetoes. Worth it once the training recipe is the
bottleneck again; until then perf-sim + one-episode-per-vCPU is the cheap 2.5-3x.
